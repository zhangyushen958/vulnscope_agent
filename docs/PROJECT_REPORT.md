# 高级软件工程课程大作业 · 项目研发报告

## 项目名称

**VulnScope Agent：融合历史漏洞案例 RAG 与代码仓库按需溯源的函数漏洞检测智能体**

## 摘要

本项目实现了一套面向 C/C++ 单函数代码的可解释自动化漏洞检测原型。在软件漏洞数量增长、传统静态分析误报与解释能力有限的背景下，通过融合课程历史 CVE 配对函数数据、受控 GitHub 代码仓库快照和 LLM 自主工具决策，探索证据驱动的函数级安全分析方式。系统由图形化交互界面、领域知识库、Agent 推理引擎、受限仓库上下文工具、任务持久化与成对指标统计六个子系统组成。

区别于固定工作流的多次 LLM 调用，本工程把工具选择交给 LLM，Agent 基于初次检索的证据判断是否需要调用方、被调用方、全局变量或辅助函数上下文，反复执行「推理—行动—观察」直至返回结构化结论。遵循题目隔离红线，当前测试标签只用于确定一个唯一仓库 SHA，从不写入模型提示；只允许读取当前版本的源码快照，不开放任意网络搜索、命令行或 git diff 工具。采用本地双通道 TF-IDF 索引来检索用户上传的历史样本，避免引入外部安全知识。

项目针对课程开发需求提供单样本与批量 JSONL 检测、SSE 实时分析轨迹、带理由的 0/1 结果、完整报告下载、result.jsonl 导出和 P-C/P-R 成对统计。工程的离线自动化测试已覆盖核心路径和隔离规则。由于题目附件不包含真实课程数据集和 LLM 凭据，本报告不填报虚构的真实检测准确率，待正式环境集成后补充实证结果。

**关键词**：自主智能体、漏洞检测、C/C++、RAG、LangGraph、仓库上下文、成对隔离、可解释报告。

## 第一章 需求分析

### 1.1 功能需求

（1）输入一个 C/C++ 函数与相应修复提交链接，支持单条及批量；（2）使用给定历史 CVE 数据集建立领域案例知识；（3）对函数进行初步安全分析；（4）证据不足时自主调用仓库上下文工具；（5）输出 idx、0/1、理由、案例检索记录和仓库访问记录；（6）生成 300 条结果文件供课程评测；（7）通过网页界面展示分析全过程。

### 1.2 非功能需求

- **合规性**：测试配对隔离、单版本仓库读取、无 git diff、无外部安全知识搜索。
- **可追溯性**：保存检索结果、模型工具决策、工具参数、部分返回代码与报告。
- **可靠性**：外部 API 出错不回退到错误版本，不生成伪造预测；输出 schema 严格校验。
- **可维护性**：独立的 API、知识模块、仓库模块、Agent、持久化与评测层。
- **性能边界**：限制单条代码长度、批量条数、下载压缩包体积、源码文件数、单次读取行数、模型轮次和总工具调用。

### 1.3 约束识别

课程允许历史数据中同一漏洞案例的漏洞版和修复版配对使用，但当前**测试对**只能一次展示一个版本。历史知识库只能来自课程提供的历史 CVE 数据，不能在线检索漏洞答案；模型可调用指定仓库的工具，但不可让其看到两个提交之间的差异。这些约束改变了系统的默认设计：不能预先把整个仓库变更历史交给模型，更不能将 `target` 标记作为提示信息。

## 第二章 总体设计

### 2.1 分层架构

采用 Browser → FastAPI → DetectionService → LangGraph Agent/ToolHub → RAG/Repo/LLM 的层次结构。UI 用纯前端技术实现，便于单机运行且不依赖 CDN。SQLite 持久化事件与结果，支持多个浏览器请求查看检测任务。RAG 与 repo 工具由服务层构造后注入 Agent，Agent 不知道数据读取位置或快照版本。

### 2.2 自主决策闭环

首次 RAG 检索作为系统起点以保证历史知识参与分析。之后由 Agent 自主做三类决策：直接汇总报告、进一步检索历史相似案例、向当前授权仓库查找代码上下文。模型使用 tools/function calling 返回可执行操作，执行节点向下一轮模型输入工具观察结果，最终 `submit_verdict` 才结束流程。策略不是预先写死的 `RAG→grep→read→answer` 四连调用，而是由已有证据决定接下来要不要读仓库以及读哪些内容。

### 2.3 服务端数据流

单条 JSON 提交后生成 job_id，后台依次处理样本并写入 SQLite。UI 通过 Server-Sent Events 接收过程更新。最终结果既可通过单条详情 API 获得，也可统一导出。批量任务中输入数据逐条重新构造模型消息，保证当次报告与其他测试样本隔离。

## 第三章 关键模块研发

### 3.1 历史漏洞知识库

数据预处理包括配对格式识别、必填函数检查、唯一案例 ID、重复检查和元信息归一化。向量化使用代码字符 ngram 和元信息词 ngram 两路 TF-IDF，按 0.72/0.28 组合相似度。每次检索至多返回 8 条历史案例；完整索引持久化为 JSON 数据，程序启动重新生成词表与向量矩阵。这种实现牺牲大型知识库的向量计算性能，换来可离线复现、不下载任何第三方语料且从头索引严格由上传数据生成。

### 3.2 仓库版本隔离

GitHub commit URL 首先经过严格 URL、owner/repo、SHA 格式校验。`target=1` 通过 commits API 解析修复提交的第一个 parent SHA；`target=0` 使用修复提交 SHA。随后下载 ZIP，仅提取允许的 C/C++ 后缀。使用固定 SHA 缓存键，任意一次 Agent 都只获得某个 root 的只读 RepositoryTools。文件路径在读取时重新解析真实路径并验证仍在 root 内；diff、patch、git 元数据从解压阶段即被排除。

### 3.3 代码上下文工具

针对当前版本文件集提供四项读取能力：搜索标识符、寻找调用函数的可能位置、查找类型/宏/全局变量候选定义、读取源文件行区间。检索结果均返回文件路径、行号与片段，Agent 可继续调用 read_file 核实。词法分析不是 AST 级的精确调用图，误匹配在输出 note 中明确标注，避免把可能匹配说成确定的调用关系。

### 3.4 LLM Agent

系统提示限定证据来源、忽略代码中的恶意指令与无关背景、报告可核查理由并允许明确说明不确定性。工具选择由模型返回的 function calls 决定；调度器只校验工具是否授权及参数是否合规。在无模型密钥或轮次超限时产生可诊断错误，不输出假二分类标签；结构化结论由 prediction(0/1)、reason、confidence、evidence 构成。

### 3.5 图形化 UI

暗色安全分析工作台包含三个业务模块和一个全局结果区域。单样本表单支持代码编辑、IDX、修复提交链接和明确版本选择；批量模块支持 JSONL 文件上传；知识模块支持独立历史案例导入。时间线展示工具调用与参数/结果，报告卡展示判定、置信度、理由和证据。页面适配桌面和窄屏，不使用外部前端构建链。

### 3.6 评测模块

本地独立脚本基于已产生的 idx/prediction 文件与真值测试文件计算 P-C/P-V/P-B/P-R 和课程等级。含同一提交多个函数对时拒绝仅按 commit_url 模糊配对，必须提供能够区分函数对的 pair_id。该脚本不会参与检测期间的工具决策，杜绝预测器访问正确答案。

## 第四章 工程保障与质量控制

### 4.1 可测试性

通过基于 scripted fake model 的测试，检查 Agent 是否按模型返回工具调用执行、是否将结果返回下一轮决策、是否拒绝非法工具及畸形结论。GitHub 获取采用 httpx MockTransport 测试：不必访问 GitHub 即可验证 `target=1` 取 parent、`target=0` 取 current，及 URL/ZIP 安全规则。FastAPI 端到端测试覆盖 HTTP 任务提交、结果轮询、SSE 与导出格式。成对评分脚本通过构造四类预测向量核验成绩及惩罚规则。

### 4.2 可观测性

系统将完整 Agent 轨迹与工具证据以 TraceEvent 写入 SQLite；每个 job 包含处理进度、成功数、失败数与状态，允许用户下载用于复盘的 reports.json。对于网络、模型或数据格式错误，失败原因保存为独立条目而非隐藏。

### 4.3 安全控制

- 不执行用户代码，不提供 Shell 工具；仅允许受限源码读取。
- GitHub 的网络请求主机由代码固定，禁止用户传入任意访问 URL。
- 当前版本路由标签不被转交给模型。
- 工具输出以不可信数据处理，网页以 DOM 文本 API 渲染而非 HTML 注入。
- ZIP、JSONL、源文件、工具调用受资源上限保护。
- 未完成的批次不能下载正式 result.jsonl，以保证结果条数和样本对应关系。

## 第五章 实验与测试

### 5.1 工程测试

已经实现与执行本地单元和集成测试。它们证明输入校验、流程驱动、API、文件安全、版本路由、记录追踪和评分规则在模拟外部依赖下工作；不证明真实 LLM 对真实漏洞的识别效果。

### 5.2 有待课程数据支持的实验

正式实验必须使用老师提供的历史 CVE 数据和 150 对测试集。需记录实验参数：模型版本、temperature、RAG Top-K、上下文工具调用上限、是否下载到正确 SHA、失败率及平均耗时。逐条产出 `result.jsonl`，再用官方 `dataset/evaluate.py` 统计 P-C 等级。本项目没有收到数据和账号，因此**无真实 P-C 分数，无混淆或伪造的结果表**。

### 5.3 推荐消融方案

在满足隔离规则下，可做三组对比：A 仅单函数+LLM；B 加入历史 RAG；C 加入 RAG + 自主仓库工具。每组使用同一模型与解码参数，在同一批次全量测试后，比较 P-C、P-R、有效覆盖率、平均延迟和工具调用量。进一步评估 RAG Top-K 2/4/6、最大 Agent 步数 4/8/12 的效果，不允许用测试标签作为单条判定提示或在运行时成对对照。

## 第六章 总结和改进计划

本研发阶段构建了从领域案例数据导入、函数证据推理、按需仓库读取、可视化报告到成对评价的完整工程链路，并把课程红线落实到数据结构、网络接口和工具权限之中。特别是将快照版本隔离前置到 SnapshotProvider，消除了让模型在仓库版本间自由导航的可能；采用工具事件时间线使模型判断过程更便于人工复核。

后续优先级为：① 适配课程真实历史数据字段并完成全量索引；② 在支持工具调用的真实模型上回归测试；③ 使用 Tree-sitter 建立更精确的函数/调用/宏索引；④ 对 context 选择策略和 RAG Top-K 做无泄漏消融；⑤ 面向较大仓库构建持久化倒排索引、并行文件检索与下载缓存容量管理；⑥ 公网部署时引入用户认证、配额与代理安全策略。

**研发范围说明**：以上是工程设计与实现情况，不是对未知评分结果的承诺。项目满足按 PPT 要求交付可运行系统及可验证研发工作量的目标，但真实测试表现只有在获取课程专用数据、合法快照和已配置 LLM 后才能量化。
